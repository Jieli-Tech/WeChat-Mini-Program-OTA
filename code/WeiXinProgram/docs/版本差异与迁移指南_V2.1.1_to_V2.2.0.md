## 1. 总体结论

**V2.2.0非必须升级版本。部分旧项目推荐保持使用v.2.1.1版本即可**

V2.2.0 核心变化有三点：

1. **封装层下沉**
   V2.1 放在示例工程里的 `lib/otaWrapper.ts`、`lib/reconnect.ts`、`lib/jl_lib/jl_auth_2.0.0.*`（OTAWrapper、回连、认证）全部合并进 `jl_ota_2.2.0_ota` 和 `jl_rcsp_2.2.0_ota`。

2. **升级数据通道改变**
   V2.1 通过 `OTAConfig.updateFileData` 一次性把整个固件交给库；V2.2 改为回调 `onReadData(offset, size)` 按块取数，`OtaConfig` 不再携带固件数据。

3. **RCSP 协议库整体换代**
   大量类名、方法名、错误码体系、日志接口、认证接口重命名/重构，同时新增大量非 OTA 模块（健康、运动、翻译等）。

> **迁移影响等级：高。**
> 只替换 `jl_lib` 会直接编译失败；必须同步改造调用层。
> 若项目基本基于官方示例，建议**以 V2.2 工程为基线，把自定义业务代码合入**，而不是在 V2.1 上逐点修补。

|---|---|---|---|

#### 1.1.1 修复导入升级文件后选中文件错乱

**问题现象**

升级文件列表重新加载后，原先选中的文件没有被正确回显为选中状态，UI 高亮错位或丢失，影响用户继续升级。

**代码层原因**

V2.1 只保存 `fileIndex`。`_onUpgradeFileInfoList()` 会对列表执行 `reverse()` 并重新 setData，列表顺序变化后，原来的索引指向了别的文件；删除文件、取消选择后也没有同步清理索引，形成脏状态。

**修复实现**

- `miniprogram/pages/pageUpdate/pageUpdate.ts` 新增 `selectFilePath`，记录当前选中升级文件的**路径**，而不是索引；
- 加载列表时按 `selectFilePath` 匹配 `element.filePath`，反算出正确的 `fileIndex` 并回显；
- 在删除文件、取消选择、文件丢失等场景同步清空 `selectFilePath`；
- 选中文件时同步记录路径。

关键代码位置：

- [pageUpdate.ts:36](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/pages/pageUpdate/pageUpdate.ts#L36) — 新增 `selectFilePath`
- [pageUpdate.ts:404-416](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/pages/pageUpdate/pageUpdate.ts#L404-L416) — 列表加载时按路径回显 `fileIndex`
- [pageUpdate.ts:176](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/pages/pageUpdate/pageUpdate.ts#L176)、[199](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/pages/pageUpdate/pageUpdate.ts#L199)、[246](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/pages/pageUpdate/pageUpdate.ts#L246) — 删除/取消/异常场景清空
- [pageUpdate.ts:258](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/pages/pageUpdate/pageUpdate.ts#L258) — 选中时记录路径

**验收口径**

- 选中 B 后退出再进入升级页，B 仍保持选中；
- 取消选择/删除选中文件后 `fileIndex = -1`，UI 无选中态；
- 导入同名但路径不同的文件后，选中状态指向原路径对应的文件，不串错；
- 选中状态下继续导入新文件，原选中项保持不变；
- 升级时仍能正确读取选中文件的 `filePath` 完成 OTA。

#### 1.1.2 拦截不允许多连接设备

**问题现象**

iOS 升级过程中存在一种场景：先连接「升级后会变地址的设备（实际不存在）」，再连接真正的升级设备并开始升级。设备重启后，前一个挂起的连接会被系统直接连上，导致设备来不及发出广播包，最终单备份回连超时失败。

**原因**

- `wx.createBLEConnection` 没有设置超时（V2.1 为 `undefined`），连接请求可以长期挂起；
- 连接过程中没有 UI 拦截，用户可以取消/再次点击连接其他设备，形成多设备连接竞争；
- iOS 在设备重启后优先建立此前的挂起连接，抢占广播窗口。

**修复实现**

- `miniprogram/lib/bluetoothOTAManager.ts`：`_ConnectSettingConfigure.timeout` 从 `undefined` 改为 `5000`，最终传给 `wx.createBLEConnection({ timeout: 5000 })`，5 秒后由系统结束挂起连接；
- `miniprogram/pages/pageConnect/pageConnect.ts`：连接时 `wx.showLoading({ title: '连接中', mask: true })`，连接未结束前遮罩拦截用户操作，避免并发发起第二次连接。

关键代码位置：

- [bluetoothOTAManager.ts:29](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/lib/bluetoothOTAManager.ts#L29) — 连接超时 5 秒
- [pageConnect.ts:119-124](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/pages/pageConnect/pageConnect.ts#L119-L124) — 连接中遮罩

**验收口径**

- 先连不存在/变地址设备，再连升级设备并升级，设备重启后不会被错误自动连接，能正常广播并回连成功；
- 连接不存在的设备时，5 秒后超时失败并触发「连接失败」；
- 连接过程中点击其他 UI 元素会被遮罩拦截。

> 说明：这是小程序端的规避措施，协议层回连逻辑未变。固件端的 BLE 地址配置、新回连广播包格式仍需正确（对应 `docs/readMe.md` 第 7、8 节）。

#### 1.1.3 兼容纯血鸿蒙（HarmonyOS NEXT）

**问题现象**

鸿蒙微信环境下，BLE 连接 MTU 设置和数据并发行为与 Android/iOS 存在差异，导致连接失败，或升级过程中丢包、错序。

**原因**

- V2.1 只在 `platform === 'android'` 时调用 `wx.setBLEMTU`，鸿蒙平台 `ohos` 不会进入该分支；
- 部分环境下 `setBLEMTU` 成功回调里 `res.mtu` 为 `undefined`，无法获取实际协商 MTU；
- 鸿蒙微信对 BLE 写操作并发支持较弱，V2.1 在发送前就 `shift()` 出队，回调节奏与队列不一致时容易丢包/乱序。

**修复实现**

- `miniprogram/lib/bluetooth.ts`：平台判断增加 `ohos`，`android` 与 `ohos` 都走 `setBLEMTU`；
- `setBLEMTU` 成功但 `res.mtu` 为 `undefined` 时，自动回退调用 `getBLEMTU()`；
- `miniprogram/lib/ble-data-handler.ts`：发送队列改为取索引 0，不再发送前 `shift()`；在 `success` / `fail` 回调中再 `shift()`；失败重试 3 次后才出队，保证串行发送与顺序；
- 配套：`app.ts` / `pageSetting.ts` / `bluetooth.ts` 在基础库 ≥ 2.20.1 时改用 `wx.getDeviceInfo()`，确保能正确识别 `ohos` 平台。

关键代码位置：

- [bluetooth.ts:238-256](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/lib/bluetooth.ts#L238-L256) — `ohos` 平台 MTU 设置与 `getBLEMTU` 回退
- [ble-data-handler.ts:102](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/lib/ble-data-handler.ts#L102) — 取队首不 `shift()`
- [ble-data-handler.ts:119-133](../JL_OTA_V2.2.0_SDK_V2.2.0/miniprogram/lib/ble-data-handler.ts#L119-L133) — 回调成功/最终失败后出队

**验收口径**

- 鸿蒙微信下连接 OTA 设备并完成一次完整升级，设备重启后功能正常；
- 模拟 `setBLEMTU` 返回 `res.mtu = undefined`，仍能通过 `getBLEMTU()` 拿到 MTU 并升级；
- Android、iOS 执行同样流程，三端结果一致。

#### 1.1.5 需要区分：这些不是本次「问题修复」

V2.2.0 与 V2.1.1 的代码差异远大于上面 3 项，但验收文档只把上述 3 项列为「问题修复」。以下属于随版本升级带来的**架构升级 / 适配 / 体验增强**，不建议写进「修复了什么问题」：

- OTA / RCSP SDK 整体升级到 2.2.0，`OTAWrapper`、`Reconnect`、`Auth` 下沉入库；
- `OTAConfig.updateFileData` 移除，改为 `onReadData(offset, size)` 按块读取；
- 错误码从负数体系切换为 `0x6000` 正数体系；
- 新增强制升级 `onMandatoryUpgrade`、RCSP 初始化 `onRCSPInit` 回调；
- 日志系统重构（`LogHub`、`Log.d/i/w/e`、日志文件页）；
- 首次扫码权限缓存 `IsHasPermission`；
- 分享、监听器注销、设置页版本号动态显示等；
- 基础库 2.20.1+ 系统 API 全面适配（其中与鸿蒙相关的部分已计入修复 3）。

这些变更会导致**接口不兼容**，集成方仍需按本文第 3–6 节完成适配。

### 3.2 升级流程：从「整包传入」到「按块回调」

#### V2.1.1

```ts
import { OTAConfig, ReConnectMsg, UpgradeType } from "../../lib/jl_lib/jl_ota_2.1.1"

const otaConfig: OTAConfig = new OTAConfig()
otaConfig.isSupportNewRebootWay = true
otaConfig.updateFileData = this.upgradeData          // 整包固件
sBluetoothManager.startOTA(otaDev, otaConfig, {
  onStartOTA: () => {},
  onNeedReconnect: (msg: ReConnectMsg) => {},
  onProgress: (type: UpgradeType, progress: number) => {},
  onStopOTA: () => {},
  onCancelOTA: () => {},
  onError: (error: number, message: string) => {},
})
```

#### V2.2.0

```ts
import { JL_OTA } from "../../lib/lib_rcsp"

const otaConfig = new JL_OTA.OtaConfig()
otaConfig.isSupportNewRebootWay = true                 // 不再有 updateFileData

// 1) 必须先确认 RCSP 已初始化，否则 startOTA 会静默 return
const isInit = await sBluetoothManager.isInit(otaDev)
if (!isInit) {
  wx.showToast({ title: '设备未初始化，请稍候', icon: 'none' })
  return
}

// 2) 读取设备是否要求强制升级（可能 reject，需 try/catch）
let mandatory = false
try {
  mandatory = await sBluetoothManager.isNeedMandatoryUpgrade(otaDev)
} catch (e) {
  mandatory = false
}

sBluetoothManager.startOTA(otaDev, otaConfig, {
  onStartOTA: () => {},
  onReadData: (offset, size) =>
    this.upgradeData.slice(offset, Math.min(offset + size, this.upgradeData.length)),
  onExecuteDisconnectDevice: () => {},                // SPP 必须实现；BLE 可为空
  onNeedReconnect: (msg: JL_OTA.ReconnectInfo, cb) => {},
  onProgress: (type: JL_OTA.UpgradeType, progress: number) => {},
  onStopOTA: () => {},
  onCancelOTA: () => {},
  onError: (error: number, message: string) => {},
  onRCSPInit: (deviceId: string, isInit: boolean) => {},
})
```

#### 回调语义说明

| 回调 | 说明 |
|---|---|
| `onReadData(offset, size)` | **同步**回调，返回 `Uint8Array`；越界返回 `undefined` 时库会用空数组兜底 |
| `onExecuteDisconnectDevice()` | 只有 SPP 通讯方式需要真正断开设备；BLE 示例为空实现 |
| `onNeedReconnect(msg, cb)` | 第二个参数 `reconnectCallback` 在**上层自行回连**时必须回调：成功 `cb.onResult(deviceId)`；失败 `cb.onError(code, msg)`。若使用 `isInnerReconnect: () => true`（官方示例），库内部用 `Reconnect` 自动处理，无需调用 |
| `onRCSPInit(deviceId, isInit)` | 本次 OTA 流程内的 RCSP 初始化结果 |
| `onStartOTA` | 真正开始升级时触发；V2.1 中点击升级即显示进度，V2.2 需等此回调 |

> 注意：`OTAWrapper.startOTA` 不会抛异常。RCSP 未初始化时只打印日志并直接返回，**升级前检查 `isRCSPInit` 是必须的**。

### 4.1 自定义命令页改造示例

参考 `miniprogram/pages/pageSetting/pageCustomCmd/pageCustomCmd.ts`：

```ts

if (command.getStatus() == RCSPProtocol.ResponseBase.STATUS_SUCCESS)

case RCSPProtocol.ErrorCode.ERROR_RESPONSE_TIMEOUT:
_status == RCSPProtocol.Connection.CONNECTION_DISCONNECT
```

回调泛型也由 `CommandCallback<CommandBase>` 改为 `CommandCallback<JL_RCSP.Command>`。

### 4.2 认证（Auth）变化

V2.1 的 `jl_auth_2.0.0` 是独立库，由 `otaWrapper.ts` 直接 `new Auth()` 并手动转发认证数据。

V2.2 中：

- `Auth`、`AuthListener`、`setLinkKey` 由 `jl_rcsp_2.2.0_ota` 导出；
- 使用 `JL_OTA.OTAWrapper` 时，认证由库内部管理（`OTAWrapperOption.isUseAuth` 返回 true 即启用），`sendData` 必须实现，否则认证数据发不出去；
- `Auth.startAuth` 新增 `supportResetFlag` 参数，库内部默认传 `true`；
- 应用层不再需要维护 `_AuthMap`、`handlerAuth` 等逻辑。

### 4.3 日志（Log）变化

V2.1 通过 `setLogger` 把应用 logger 注入 OTA / RCSP / 应用三套日志函数。

V2.2 改为统一的 `LogHub`：

```ts
export function initLog() {
  const logOption = {
    output: (level: string, module: string, tag: string, message: string, ...args: any[]) => {
      Log.logout(level, module, tag, message, ...args)
    }
  }
  JL_OTA.OtaLog.setLogOption(logOption)
  JL_RCSP.RcspLog.setLogOption(logOption)
  Log.logOptions = getLogger()
}
```

应用侧调用：

```ts
import Log from "./common/Log"
const TAG = "MyModule"
Log.d(TAG, "debug")
Log.i(TAG, "info")
Log.w(TAG, "warn")
Log.e(TAG, "error")
```

等级含义：`d = 0`、`i = 1`、`w = 2`、`e = 3`；`Log.level` 越小越详细，`Log.saveLog` 控制是否写入 `wx.getLogManager`。

## 5. 示例工程行为差异（迁移时容易被忽略）

1. **强制升级**
   V2.2 `OnRcspCallback` 新增 `onMandatoryUpgrade`，`pageConnect` 监听后自动切到升级页并提示。需要固件支持 `CmdGetTargetInfo.FLAG_MANDATORY_UPGRADE`。

2. **RCSP 初始化回调**
   `onRcspInit` 在页面注册 `OTAWrapperListener` 后即可获知设备初始化成功，V2.1 无此 UI 提示。

3. **首次扫码抑制**
   V2.2 用 `IsHasPermission` 缓存判断是否已成功扫过码，首次进入不主动触发权限弹窗，由下拉刷新触发；V2.1 每次 `onLoad` 直接 `sanDevice()`。

4. **升级前预检**
   V2.2 先 `isInit`、`isNeedMandatoryUpgrade`，再显示进度弹窗；V2.1 点击升级立即显示。

5. **扫描结果转换**
   V2.2 需要把 `BTBean.BluetoothDevice` 的 `advertisData` 映射到 `JL_OTA.BluetoothDevice.advertiseData`（字段名少了一个 `t`）。自定义回连逻辑若直接读 `advertisData` 要特别注意。

6. **连接超时**
   V2.2 `ConnectSettingConfigure.timeout = 5000`，V2.1 为 `undefined`（不超时）。

7. **蓝牙授权修复**
   V2.2 在授权成功后补调 `_openBluetoothAdapter()`，V2.1 授权成功后不会继续扫描。

8. **发送队列修复**
   V2.2 在写成功 / 重试耗尽后才 `shift()`，V2.1 在发送前就出队，异常场景可能丢包。

9. **日志等级语义变化**
   V2.1 存 1–5（`logv` ~ `loge`），V2.2 存 0–3（`logd` ~ `loge`）。**旧缓存值 4/5 在 V2.2 会导致所有日志被过滤**，升级后必须迁移或清空 `LogGrade` 缓存。

10. **日志文件页**
    V2.2 新增 `pageLogFile`，读取 `wx.env.USER_DATA_PATH/miniprogramLog`；示例工程中未找到写入该目录的代码，若需要落盘需自行实现。

11. **分享**
    V2.2 在 `pageConnect`、`pageUpdate`、`pageSetting` 增加 `onShareAppMessage`，开启转发。

12. **监听器注销**
    V2.2 `pageConnect.onUnload` 会注销 `OTAWrapperListener`，避免页面销毁后仍收到回调。

13. **设置页**
    Log 文件与 Log 等级入口由「仅开发者模式可见」改为「始终可见」；版本号由写死改为动态读取。

## 7. 重点避坑清单

1. **`startOTA` 静默失败**
   未等 RCSP 初始化就调用，只打印日志、不触发任何回调。必须先 `await isRCSPInit()`。

2. **`isNeedMandatoryUpgrade` 可能 reject**
   设备信息未就绪时会 reject，务必 `try/catch`。

3. **`onNeedReconnect` 第二参数**
   上层接管回连时必须回调 `reconnectCallback`，否则升级流程一直等超时。

4. **`onReadData` 不要返回整包**
   必须按 `(offset, size)` 切片，否则失去 V2.2 的大文件内存优化意义；同时保证 `offset + size` 不越界。

5. **`ReconnectInfo.deviceBleMac` 为空**
   单备份新回连要求固件正确配置 BLE 地址，否则回连必然超时（`docs/readMe.md` 第 8 节已说明）。

6. **`advertisData` → `advertiseData`**
   自定义回连 / 广播解析代码最容易漏改。

7. **`LogGrade` 旧缓存**
   不清空会导致新版本日志全被过滤。

8. **`onExecuteDisconnectDevice`**
   如果将来接 SPP，必须实现真正断开；BLE 可空实现。

9. **`OTAConfig` 改名 `OtaConfig`**
   TypeScript 编译报错集中点。

10. **文档引用过期**
    V2.2 `docs/readMe.md` 第 8 节仍写「otaWrapper.ts 中搜索 isReconnectDevice」，该文件已不在示例工程，实际位于 `JL_RCSP` 库源码中；自定义回连请通过 `OTAWrapperOption.isInnerReconnect = () => false` + `onNeedReconnect` 实现。

11. **认证与数据通路不要重复**
    使用 `OTAWrapper` 且 `isUseAuth` 为 true 时，认证数据由 `sendData` 发出。若上层同时维护自己的 `RcspImpl` 并转发 BLE 数据，注意不要与 `OTAWrapper.onReceiveData` 形成双份投递。

12. **`getRCSPImpl` 外部托管模式**
    若实现 `OTAWrapperOption.getRCSPImpl`（例如接入 `jl-rcsp-op`），需自行调用 `onRcspInitSuccess` / `onRcspInitFail`，库不会再创建内部 `RcspImpl`。
